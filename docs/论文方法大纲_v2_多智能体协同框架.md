## 标题与摘要

**标题方向**
面向高速公路桥梁全流程设计的大语言模型多智能体协同框架构建与实现

**摘要要点（工程化表述）**
- 问题：桥梁设计路线、地形、障碍物、结构计算与规范条文等资料来源多；设桥布跨、下部结构设计、配筋设计与验算分析等环节前后强依赖；人工组织与反复校核工作量大。
- 方法：把全流程拆为可协作的设计阶段，以设计协调智能体统一调度，大语言模型承担需求理解、方案生成与反馈判断，确定性工具承担资料解析、碰撞检测与结构验算；通过统一状态、阶段交接契约、成果依赖关系与人工复核机制串成完整闭环。
- 结果：以真实工程区段为输入，实现从线路资料到结构化设计成果的连续生成，展示布跨修正、结构设计与承载力验算反馈的完整过程。
- 结论：方法具备可行性、可复现性，为桥梁设计由局部自动化走向全过程智能协同提供可实现路径。

**关键词**
桥梁设计；大语言模型；多智能体；设计协同；成果依赖；反馈修正；人在环

## 1 绪论

### 1.1 研究背景
- 交通强国、国家综合立体交通网、交通基础设施数字化转型背景（沿用 v1 可复用段）。
- 重点落在**高速公路桥梁设计流程的工程痛点**：资料来源多、专业链条长、阶段成果依赖强、人工组织与反复校核工作量大。

### 1.2 研究现状
沿用 v1 的分层述评，收尾固定落到"现有方法多为单环节/预设条件下的自动化提效，缺全过程连续生成"：
1. BIM / 参数化建模（[4-5]）；
2. 程序化有限元建模 + 智能优化（[6,11]）；
3. 强化学习布跨（[7-8]）、生成对抗/条件生成等数据驱动局部生成（[9-10]）；
4. LLM 在土木工程中的探索（知识问答、剪力墙结构、铁路桥梁校核 [14-16]）；
5. 多智能体 LLM 框架在结构/岩土/能耗/BIM 场景的探索（[17-20]）。

### 1.3 问题分析（对应更新）
保留 v1 的两条，第三条措辞升级：
1. **全流程缺口**：桥梁设计环节前后依赖，现有智能设计研究多集中于单一环节或施工运维，未充分解决阶段间信息传递、结果反馈与连续生成。
2. **生成与确定性的矛盾**：LLM 具备理解与生成能力，但工程任务涉及路线几何、CAD 图纸、障碍物空间关系、结构内力与承载力验算等多模态强约束信息，需专业知识库、工程样本、结构化提示与外部计算工具的补充；更进一步，**LLM 参与流程调度决策时，其决策本身需要确定性约束与兜底**（本条为 v1 → v2 的新增升级点）。
3. **多智能体协同的可靠性**（新增）：现有 LLM 多智能体框架以自治对话为主，存在流程不可控、返工范围无依据、过程不可审计的问题，难以直接用于设计结果可能进入施工图的工程场景。

### 1.4 本文工作与贡献
1. 构建面向桥梁全流程设计的多智能体协同框架，以**设计协调智能体为调度中枢**，组织初步设桥布跨、布跨检测修正、下部结构设计与承载力验算反馈等阶段，实现跨阶段设计信息的连续传递与动态调度。
2. 建立面向桥梁设计任务的知识样本与提示生成机制，通过**提示统一注册渲染与技能注册体系**，使大语言模型在规范条文、工程样本与结构化输入约束下参与设计决策，并结合外部工具完成几何检测与承载力验算。
3. 建立**共享状态与统一阶段交接契约**驱动的跨阶段记忆与多层反馈机制，结合**成果依赖图**实现最小返工、结合几何碰撞检测与承载力验算结果实现前置方案反馈。
4. 建立**人在环与断点续跑**机制，支持人工复核决策与长时任务的持久化恢复，保证过程可审计、中断可恢复。

## 2 多智能体协同设计框架

> 本章定位：回答"系统长什么样、任务怎么流转"，讲清静态结构与流程骨架，不展开单一支撑技术的实现细节。

### 2.1 桥梁设计任务与依赖结构分析
- 先给领域侧的地基：真实流程 `线路资料解析 → 设桥布跨 → 下部结构尺寸拟定 → 配筋设计 → 建模验算`。
- 画出各环节的**输入 / 输出 / 依赖关系**，重点强调"布跨决定墩位与结构设计对象，尺寸与配筋影响承载力验算，验算结果又反推布跨与结构修正"这条**反馈依赖**。
- 落点：正因为这条依赖链的存在，后面的"成果依赖图 + 最小返工"才有工程依据（为第 3.4 节背书）。
- 配图：图 1 桥梁全流程设计依赖链（领域侧）。

### 2.2 系统总体架构
- 从 v1 的"线性流水线"改为**分层架构 + 协调器循环**：
  - 协调层（设计协调智能体）：解析需求、动态调度、确定性校验；
  - 阶段设计层（四个专业智能体，内部为子图）：布跨、修正、结构设计、验算；
  - 工程工具层（确定性工具链）：资料解析、碰撞检测、结构验算；
  - 支撑层（横切）：知识库、样本库、规范 RAG、提示/技能注册、状态与交接。
- 关键变化点：协调器是**循环中枢**——每个专业阶段完成后**回到协调器重新决策**，而非一次性规划后顺序执行。
- 配图：图 2 多智能体协同设计总体架构（分层 + 工具）。

### 2.3 阶段智能体设置与功能分配
- 智能体划分表（v1 五类表升级为"协调器 + 四专业阶段"）：

| 智能体 | 功能定位 | 主要输入 | 主要输出 |
|---|---|---|---|
| 设计协调智能体 | 解析需求、动态调度、校验决策、触发返工/复核 | 用户任务、成果状态、阶段交接 | 调度决策、阶段目标 |
| 初步设计智能体 | 生成初步设桥布跨方案 | 线路资料、障碍物信息、知识样本 | 桥位区间、跨径组合、墩位布置 |
| 布跨修正智能体 | 检测并修正布跨方案 | 初步布跨、碰撞检测结果 | 修正指令、修正后布跨 |
| 结构设计智能体 | 完成下部结构尺寸与配筋设计 | 布跨结果、设计单元、样本规范 | 盖梁/墩柱/基础尺寸及配筋 |
| 建模验算智能体 | 承载力验算并形成反馈判断 | 配筋、内力、验算参数 | 验算结果、反馈决策 |

- 补充**契约边界**：每个专业智能体声明"可读状态键 / 可产出状态键 / 允许调用的工具动作"，防止越权调用（对应代码 AgentContract + ActionSpec）。
- 说明智能体内部结构：四个专业智能体内部均为 LangGraph 子图（顺序/循环），对顶层只暴露统一交接结果。

### 2.4 动态执行路径组织
- v1"动态选组合"升级为：**协调器依据用户意图与当前成果状态动态调度**。
- 说明意图 → 阶段序列的映射（full_design / layout_design / structural_design / verification 等），以及**确定性校验**如何保证路径合法：不跳越前置阶段、不跳过强制验算、返修目标一致、轮次不超限。

## 3 关键方法实现

> 本章定位：回答"横切支撑能力各自怎么实现"，按支撑维度分节，不与第 2 章的流程组织重复。每节固定四要素：**要解决的工程问题 → 实现机制 → 与设计流程的结合点 → 设想的实现效果**。

### 3.1 设计知识库、工程样本库与规范知识服务

**（1）设计知识库与工程样本库**
- 设计知识：规范条文、尺寸/配筋经验规则的组织与结构化。
- 工程样本库：few-shot 样本（尺寸设计、配筋设计样例）的组织、选择与注入（对应 samples/ 与 select_samples 动作）。
- 效果设想：为 LLM 生成提供领域先验与案例参照，降低通用模型在专业任务上的不确定输出。

**（2）规范四库 RAG 知识服务（专业知识强化，非重点）**
- 现状（如实表述）：已完成规范条文结构化、SQLite FTS5 关键词索引、BGE 向量索引、RRF 混合检索，构建 1908 个源实体、644 份证据文档，固定评测 30/30。
- 论文表述口径：**作为专业知识强化手段已构建并独立验证，逐阶段接入设计/配筋/验算流程的"证据门控"为后续工作**（当前未接入专业 Agent 主流程，不得写成已生效闭环）。
- 设想效果：为设计决策与验算结论提供可溯源的规范证据，提升结果可解释性。

### 3.2 多源工程数据预处理与语义组织
- 基本沿用 v1：线路资料解析、图纸预处理（DXF 转换、Mask 生成）、障碍物语义识别与组织。
- 强调这些是**确定性工具链**，由工具层执行，结果写入共享状态供 LLM 读取。
- 效果设想：把多源异构输入统一为 LLM 可理解的结构化语义信息（桩号、障碍物、桥位约束），作为布跨生成的基础。

### 3.3 面向桥梁设计任务的提示机制与技能体系
- **提示统一注册与渲染**：prompts/manifest.yaml 统一注册任务模板，PromptRegistry 以严格 Jinja2 渲染，产出带版本与内容哈希的可追溯提示（对应代码 RenderedPrompt 的 template_sha256）。
- **技能注册体系**：skills/<name>/SKILL.md 定义各智能体的角色、职责边界、决策规则与证据使用规则，由 SkillRegistry 校验加载；动作权限真源收敛到统一动作注册表（对应 SkillRegistry 与 AGENT_ACTIONS 的职责分离）。
- 效果设想：提示可版本化管理、可追溯；智能体角色与权限有明确边界，避免 LLM 越权调用工具或产生无法解释的产出。

### 3.4 共享状态驱动的记忆协同与反馈修正机制（升级最大的一节）

**（1）统一共享状态与阶段交接契约**
- 共享状态承载用户任务、桩号范围、图纸处理结果、障碍物语义、布跨结果、碰撞指标、设计单元、尺寸/配筋结果、验算结果与反馈决策，各智能体读写同一状态形成跨阶段记忆（沿用 v1 表述）。
- 新增：**统一阶段交接协议（StageHandoff）**——每个专业智能体完成后统一产出 `stage / status / 产出成果 / 返修请求 / 失效成果 / 建议下一阶段`，其中"建议下一阶段"仅为建议，跳转决定权收归协调器。
- 效果设想：阶段间信息传递由松散的状态字典升级为结构化协议，协调器能统一读取与校验各阶段结果。

**（2）成果依赖图与最小返工**
- 定义成果依赖链：`路线障碍资料 → 布跨方案 → 设计单元 → 尺寸方案 → 配筋方案 → 分析结果 → 验算结果`。
- 失效传播：上游成果变更时，可计算地失效全部下游成果；返工范围由依赖图给出**最小返工路径**，而非全量重跑。
- 状态清理：失效成果对应的状态键与路径一并清空，避免下游工具继续读取旧文件。
- 效果设想：验算不过时只回退到配筋/尺寸等必要环节，而非从头重跑——这是"最小返工"从口头承诺变成可计算性质的关键。
- 现状标注：依赖图与失效传播已完成，**接入真实运行路径的自动最小返工为后续工作**。

**（3）结构分析与综合验算反馈闭环**
- 下部结构尺寸与配筋完成后，调用 OpenSeesPy 等专业分析软件，提取内力包络、位移响应、支座反力、墩柱受力、控制工况与承载力利用率。
- 识别配筋不足/截面不足等局部问题，并进一步判断跨径组合、墩高分布、结构体系、桥位布置等前置因素是否合理。
- 效果设想：形成"验算 → 反馈 → 修正 → 复验"的完整闭环，验算结果直接驱动前置方案修正（沿用 v1 并写实）。

**（4）人在环与断点续跑**
- 人工复核：对碰撞修到上限仍有残留、连续非法调度、验算失败且无法自动修正等边界场景，系统挂起等待人工决策（继续修正 / 接受当前方案 / 终止任务），工程校核指标始终保留原值、不因人工放行而篡改。
- 断点续跑：双层恢复机制——成果层从输出目录扫描恢复已有成果，图状态层通过持久化 checkpoint 恢复运行指针。
- 效果设想：长时设计任务中断后可续跑；人机分工明确，不可裁量边界由人工兜底，过程可审计。
